## SOPS across hosts

SOPS encrypts configuration at rest; runtime delivery, identity and rotation are infrastructure responsibilities. The official Ansible lookup requires the SOPS executable on the controller and can decrypt into variables; its output must stay protected. [Ansible SOPS lookup](https://docs.ansible.com/projects/ansible/latest/collections/community/sops/sops_lookup.html)

Proposed delivery contract:

1. The approved controller resolves an existing concern-specific vault record using its existing authorized key. Core stores only the nonsecret reference and variable schema. Do not copy age private keys or the full encrypted vault to s60/s62 or core merely to deliver an application secret.
2. Select only the environment's allowed fields. Parse structured data directly; never use shell `eval`, `source`, debug output or secret-bearing command arguments. Missing, empty or placeholder required fields fail deployment before file replacement. Disable persistent fact caching for secret values.
3. Render the selected runtime format with `no_log: true`, `diff: false`, explicit quoted mode, owner/group and atomic replacement; leave `unsafe_writes` disabled. Do not create plaintext Ansible backup copies. Check-mode must remain read-only and must not disclose plaintext in prediction output. Ansible copy supports safe file operations and explicit permission control. [Ansible copy](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/copy_module.html)
4. Choose the runtime identity before selecting a path. Current `.env` is restricted to pavel; a future dedicated service user requires a deliberate new file/ownership contract. A proposed systemd environment file can be root-owned `0600` when the system manager reads it; an application-read file must instead be accessible to the exact service identity. Parent directories, ACLs, symlinks, hardlinks and service sandbox rules must be tested. Do not make credentials group/world-readable to bypass a startup error.
5. Validate names/format without outputting values, then reload/restart only the selected private service if its configuration changed. Test synthetic functionality as the actual service identity. Logs record a nonsecret secret-version identifier and result, never secret hashes or values.
6. Keep s61's reverse proxy free of application/DB secrets. Deliver OCR workers only credentials they require. A separate DB host receives its own provisioning/runtime credentials; each environment has independent identities. Root on a host remains trusted to access local plaintext.
7. Rotation is create new credential, deliver, verify a new connection/job, revoke old credential, then verify old access is rejected. Rollback before revocation can restore the prior encrypted version; after revocation it requires issuing a valid replacement. Remove superseded plaintext and temporary files. SOPS recipient updates or data-key rotation do not rotate the external database password. [SOPS key management](https://getsops.io/docs/)

Required automated tests before this role is adopted: missing key/field fails closed; hostile quote/newline values never execute shell; logs and `--diff` contain no synthetic sentinel secret; exact host scoping; first delivery changes once and second converges; failed validation retains the working file; excluded users cannot read it; the runtime can; rotation and failed reload recovery are exercised with disposable credentials. No SOPS consumer is claimed deployed by this document.

## Database location and access

**Recommendation (inferred):** for the first PostgreSQL runtime, prefer a dedicated Prace database on an infrastructure-owned s62 cluster if capacity, existing cluster ownership and version compatibility are verified. Co-location avoids an unnecessary network dependency while OCR concurrency is modest. This is a proposal, not a finding that such a cluster is configured. Move to another host only for a stated capacity, maintenance or availability requirement; another database name on a shared host does not supply high availability.

For local access, prefer a Unix socket with an explicitly mapped service identity where supported by the selected application settings, otherwise restricted loopback authentication. For cross-host access, bind only the selected private address, allow the exact application source in host firewall and `pg_hba.conf`, use SCRAM credentials and TLS with client certificate verification (`sslmode=verify-full` and trusted CA). Never expose PostgreSQL through the public web route. HBA rules use the first match with no fallback after failed authentication, so ordering and negative access tests matter. [PostgreSQL HBA](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html), [PostgreSQL TLS verification](https://www.postgresql.org/docs/current/libpq-ssl.html)

Create separate environment databases and runtime roles; no superuser, replication or cluster administration privileges for the web/worker process. Use a separately delivered migration identity if the deployment requires schema ownership; verify grants for future tables/sequences as well as current objects. Pin a PostgreSQL version and application driver compatible with the **selected Django release**, not the newest package by assumption. The app owns Python requirements; infrastructure owns OS client/server packages and service lifecycle. [Django database compatibility](https://docs.djangoproject.com/en/5.2/ref/databases/)

Do not install Redis or a new broker merely because OCR workers exist: current evidence identifies an ORM broker. Confirm the app's queue requirements first. If concurrency causes SQLite locking, measure that failure and move the agreed runtime to PostgreSQL rather than making the database directory broadly writable.

## Migration and recovery sequence

Schema migration and engine/data migration are different operations. Django migrations apply versioned schema/data operations to a selected database; they do not transport an existing SQLite database into PostgreSQL. Migration behavior also varies by backend. [Django migrations](https://docs.djangoproject.com/en/6.0/topics/migrations/)

1. **App supplies a nonsecret release manifest:** clean commit, immutable dependencies, settings module, source and target DB identity/path (no password), schema frontier, migration plan, protected media paths, service identities, worker stop/drain behavior, synthetic acceptance tests, desired RPO/RTO and rollback compatibility. Root development DB and synthetic-review DB must not be conflated.
2. **Infrastructure provisions isolated target:** empty test database, restricted access, protected media area, secret delivery, resource limits and backup schedule. Prove actual runtime authentication and a read-only query, wrong-role denial and inaccessible public port. `pg_isready` or an active umbrella unit alone does not establish this.
3. **Schema rehearsal:** use an isolated synthetic database under the explicit settings module; run the app-supplied migration plan and transition tests, including any intermediate migrations. Record exit codes, release and final frontier. Never create migrations on the server or auto-run a bare migration on every web startup.
4. **If data must move from SQLite:** application provides a reviewed import/export transformation. Rehearse with synthetic equivalents covering foreign keys, uniqueness, Unicode Czech/German text, timestamps/time zones, decimals, JSON, content types, tenant boundaries, file references and sequence next-values. Do not assume a generic dump/load preserves all semantics or load sensitive fixtures into ordinary CI artifacts.
5. **Cutover:** stop/drain all writers and OCR jobs for the exact environment; take a consistent recoverable DB-plus-files snapshot; import once into the selected target; validate counts/invariants and a synthetic journey; switch selected service configuration; start private services and observe errors/queue recovery. Schema evolution and backend move should be separate rehearsed steps where practical.
6. **Rollback:** prior to new writes, switch back only if old DB/release remain coherent and tested. After new writes, reverting a connection string can lose changes; stop writers and use an agreed reconciliation or forward-repair procedure. Reverse migration is not assumed safe.
7. **Recovery proof:** restore to an isolated database and protected files directory, then run app assertions as the runtime user. PostgreSQL `pg_dump` provides a consistent single-database snapshot, but excludes cluster globals and does not synchronize external documents. Add explicit role recreation and a coherent file manifest; use a truly independent encrypted backup destination. SQLite requires its online backup mechanism or another demonstrated consistent method. [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), [SQLite backup API](https://www.sqlite.org/backup.html)

Infrastructure acceptance requires query/schema health, protected storage permissions, worker error/timeout metrics, migration evidence, encrypted backup freshness, an actual isolated restore and tested alert delivery. Public holding-page `/ready` remains only nginx liveness. None of the design above authorizes exposing private review or applying migrations to an unidentified DB.
